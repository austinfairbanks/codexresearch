# Soleresearch AI Tools Reliability Plan

- **Plan ID:** `SOLERESEARCH-AI-TOOLS-001`
- **Revision:** `r1`
- **Status:** approved by the maintainer on 2026-07-11
- **Purpose:** remove orchestration friction discovered during the isolated three-branch stock-research product demo without changing the human-facing research experience or export format.

## Outcome

Agents receive a bounded, secret-free task context; can preflight a result against that exact task before admission; can safely land independent parallel additions; and cannot corrupt the run/gate lifecycle while resolving review decisions after a hard-cap pause.

## Invariants

- Existing UI, outline, source/evidence views, and exports remain unchanged.
- Canonical project state is mutated only through the existing controller-authorized broker.
- Worker material contains no controller token, canonical filesystem path, credential, or implicit authority.
- The broker remains authoritative: standalone preflight never admits a result.
- Stale updates, moves, links, retirements, restorations, merges, and colliding additions remain reviewable rather than silently rebased.
- No new dependency, live retailer access, model work, Git action, or provider-specific integration.
- Worker-reported usage remains explicitly untrusted in v1; tamper-resistant provider accounting is deferred.

## Phase unit

### 1. Atomic lifecycle derivation

Centralize gate-status derivation from run state and pending work. A paused run always has a paused gate even while pending decisions are rejected or otherwise resolved. Add a regression for the demonstrated hard-cap plus stale-result rejection sequence.

### 2. Task-aware preflight and worker context

Add a secret-free immutable worker bundle generated by an authorized run command. The bundle contains the task packet, only explicitly referenced source/evidence material, the result contract, and a minimal result template. Add optional bundle-aware `tools validate-result` checks for task identity, lease/trusted receipt time, required operations, capability/artifact/domain limits, reservation limits, source provenance, and result semantics. Structural-only validation remains backward compatible.

### 3. Conservative parallel-add admission

When a result is based on an older graph revision, rebase only a pure set of node additions whose node IDs are new, parents still exist and are active, and requested sibling positions do not collide with current active siblings. Revalidate the rebased proposal against the current graph. All other stale proposals retain existing review behavior.

### 4. Verification

Add focused failing-then-passing tests, run the complete Soleresearch test suite, replay the three-branch admission and paused-decision scenarios in temporary local projects, and obtain read-only correctness and outside-perspective reviews.

## Success criteria

- A worker can receive everything needed for an assigned local-source task without learning a controller secret or canonical path.
- A future timestamp or out-of-task artifact/capability fails bundle-aware preflight before broker admission.
- Three non-overlapping pure-add results dispatched at the same base revision can all apply under the Sol controller.
- A position collision or any non-add stale operation is not automatically rebased.
- Rejecting pending results after a hard-cap pause leaves state and gate valid and paused.
- Existing CLI, UI, outline, and export tests remain green.

## Stop condition

Stop after the reliability unit passes focused/full tests and both reviews have no unresolved must-fix finding. Do not expand into provider billing APIs, richer source search, UI redesign, or general research-method changes in this unit.
